## Operator instructions

1. Open **Forms → Entries** for the intended Gravity Form. The separate **NEW — newly created Entries** panel appears alongside native Apply. It does not use checked rows, page number, or current search filters: NEW is always whole-form, active Entries. Legacy, manually selected Flat ZIP, native Bulk Download and independent all-matching remain untouched.
2. Click **Check NEW**. The server takes a single consistent GF Entry snapshot, enumerating *all existing identities including inactive Entries* and independently cross-checking active identity selection with GFAPI. It displays the actual new eligible **Entry count** and distinct eligible **file count**. It checks each planned source with the existing Flat ZIP planner.
3. For a nonzero file count, click **Download verified ZIP**. A short-lived, user/form-bound operation revalidates the same frozen Entries, archive names and source hashes. The existing ZIP writer produces a flat archive and verifies its members and hashes before sending. The browser receives the bytes and verifies SHA-256, then prompts for manual verification. **A browser hash match does not prove the ZIP was actually retained on disk.**
4. Inspect your locally saved ZIP. Only then check the separate confirmation checkbox and click **Confirm receipt and advance NEW**. No selection, preparation, HTTP 200 or browser download automatically advances coverage.
5. If the operation contains **new eligible Entries but zero files**, no fake empty ZIP is sent: explicitly review the no-file outcome, check the box and confirm. If there are *zero NEW Entries after initialization*, the check is read-only and needs no repeated acknowledgment.
6. If the browser/download is interrupted, files changed or confirmation is absent, run **Check NEW** again. There is no permanent advancement without a valid, operation-bound acknowledgment.

## Exact identity contract

The non-autoloaded, per-form `gfbrc_new_coverage_{form}` option uses lossless sorted integer ranges. It distinguishes `known` (identity existed in the last confirmed pre-download snapshot, regardless of active/spam/trash status) from `covered` (eligible Entry identity actually included in the acknowledged operation). Entries that were previously known but become eligible or acquire uploads later do **not** reappear as NEW. Entries newly visible since the previous confirmed snapshot, including backdated GFAPI inserts and delayed lower-ID commits, remain discoverable without timestamp or maximum-ID shortcuts.

One **authoritative InnoDB-backed, non-autoloaded per-form option** `gfbrc_new_pending_{form}` holds exactly one active operation generation (random 128-bit ID), operator/form binding, 15-minute absolute expiry, coverage-base hash, frozen IDs, source fingerprint and verified ZIP SHA-256. Its value never contains stored ZIP bytes. Prior experimental transients are ignored and may expire normally. An expired pending row remains inert until a new preparation replaces it; it does not authorize late downloads or ACKs.

A new preparation captures both coverage and pending generation **before** the expensive GF snapshot and ZIP plan, then transactionally locks coverage followed by pending and only publishes if both captured states are still current. A verified ZIP may change `prepared → ready` only while its own generation holds the pending row's InnoDB lock; superseded ZIPs explicitly fail and cannot resurrect older pending state. An acknowledged download transaction locks the same two rows in the same order, validates exact generation, user/form/expiry, source and ZIP identity, then commits both the `known/covered` coverage revision and the pending operation's `acknowledged` status **atomically**. A stale acknowledgment cannot commit even if it read the old operation before a different tab prepared a replacement. Same-generation duplicate acknowledgment remains idempotent. No multi-user ledger or extra custom database table is used.

The **first run** proposes all currently eligible existing Entries as an unacknowledged initial batch. The initial empty persisted option stores *no acknowledged coverage*; identities are recorded only after explicit confirmation. Selected and current all-matching are independent and never move NEW coverage, even when the operator downloads their ZIP. Dedicated ALL was subsequently implemented in PR #28 and released alongside NEW in public v2.2.0. ALL is independent of NEW coverage/ACK state; see [DEDICATED_ALL_DOWNLOAD.md](DEDICATED_ALL_DOWNLOAD.md). This paragraph documents the original NEW-first semantics and does not override the later release.

## Resource envelope and limits

The merged source deliberately fails closed above 500 NEW eligible Entries per operation, 50,000 currently stored historical Entry identities, 1 MiB canonical coverage JSON, or 128 MiB verified ZIP. It does **not** silently divide or cover unexported portions, and does not promise availability for extremely large forms. It requires the installed GF Entry table, InnoDB consistent snapshot and local upload files. Remote/offloaded files, external persistent object cache, direct SQL import/restore identity rewriting, storage engines other than the pinned MariaDB/InnoDB or other host versions remain **NOT_PROVEN**. The pending database row is logically expired after 900 seconds, not automatically removed; it is replaced by the next generation and removed on explicit plugin uninstall. Without a download, no ZIP artifact is stored persistently.
