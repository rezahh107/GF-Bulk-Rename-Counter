# راهنمای مالک — انتشار کنترل‌شده افزونه

این مخزن یک افزونه وردپرس دارد. نسخهٔ معتبر برای آماده‌سازی انتشار از سرآیند `Version:` در `gf-bulk-rename-counter.php` خوانده می‌شود و باید با ثابت `GFBULKRENAME_VERSION` و مقدار `Stable tag` در `readme.txt` یکسان باشد. انتشار فقط از مسیر **GitHub Releases** تعریف شده است؛ هیچ انتشار در WordPress.org یا نصب روی سایت واقعی انجام نمی‌شود.

**وضعیت واقعی در ۲۴ اکتبر ۲۰۲۶:** آخرین نسخه عمومی [v2.1.1](https://github.com/rezahh107/GF-Bulk-Rename-Counter/releases/tag/v2.1.1) است؛ Selected چندصفحه‌ای آن منتشر شده. نسخه v2.1.1 ابتدا پس از ساخت Tag خطای تأیید نهایی داشت و سپس با [اجرای موفق بازیابی و فعال‌سازی همان ZIP عمومی](https://github.com/rezahh107/GF-Bulk-Rename-Counter/actions/runs/40080474995) بدون جایگزینی Tag/ZIP/Asset تأیید شد و نشانگر Candidate پاک شد. PR #24 در ۲۴ اکتبر قابلیت NEW با تأیید جداگانه دریافت را فقط به سورس `main` افزود؛ NEW هنوز در نسخه عمومی یا سایت واقعی مالک نصب نشده. نسخه v2.1.0 نیز در تاریخچه Release حفظ شده است. تگ‌ها و فایل‌های هر دو نسخه نباید جابه‌جا یا جایگزین شوند. **اشکال عمومی تأیید بلافاصله پس از Tag در Workflow انتشار اصلی هنوز برای نسخه‌های آینده اصلاح نشده**؛ پیش از انتشار بعدی آن را جداگانه اصلاح و آزمون کنید. مراحل زیر مربوط به انتشار بعدی با مجوز مستقل مالک‌اند.

## ۱. Dry-run بی‌خطر
در **Actions → Release contract and installable ZIP dry-run → Run workflow** روی `main` اجرا کنید. این عملیات فقط ZIP واقعی، فایل SHA-256 و Manifest را در **Artifacts** همان اجرای CI ایجاد می‌کند. Tag یا GitHub Release نمی‌سازد. CI مربوط به Native WordPress نیز ZIP تولیدشده را واقعاً داخل محیط آزمایشی نصب می‌کند.

## ۲. آماده‌سازی Release Candidate
در **Actions → Prepare reviewed WordPress release candidate → Run workflow** روی `main`، نیت انتشار را انتخاب کنید:
- `first`: فقط زمانی که هیچ Tag/Release قبلی وجود ندارد؛ نخستین انتشار **نسخهٔ معتبر موجود در سورس هنگام اجرا** است، نه یک شماره نسخه ثابت در این راهنما.
- `patch` / `minor` / `major`: وقتی Releaseهای قبلی وجود دارند؛ نسخه بعدی محاسبه می‌شود.

**اکنون `first` برای این مخزن معتبر نیست** چون `v2.1.1` از قبل منتشر شده است. برای انتشار بعدی فقط یکی از `patch` / `minor` / `major`، مطابق تصمیم جداگانهٔ مالک، کاربرد دارد. این راهنما اجازهٔ افزایش خودکار نسخه یا ایجاد Release نمی‌دهد.

سیستم برای هر Candidate یک Branch مستقل می‌سازد که **شماره نسخه و شناسه کامل Commit مبنای کد** را در نام دارد (مثل `release-candidate/v2.1.0-from-<base-commit>`). بنابراین Branch/PR تاریخی نسخه مشابه، مانع ساخت Candidate تازه نمی‌شود. فایل `release/candidate.json` همچنان نسخه، Branch و Commit/درخت دقیق مبنا را نگه می‌دارد. در انتشار فقط **یک PR مرج‌شده با همین Branch و همین Commit مبنا** معتبر است؛ وجود بیش از یک مورد یا هر ناسازگاری عملیات را متوقف می‌کند.

سیستم Branch و PR بازبینی را ایجاد می‌کند و دو تست `release-dry-run` و `native-zip-integration` را روی **Head دقیق Candidate** اجرا می‌کند. پایان این مرحله **به معنی تأیید تست‌ها نیست**: نتیجه هر دو Workflow را در Actions بررسی کنید. سپس تغییرات نسخه، changelog و PR را مرور کنید؛ فقط با تأیید آگاهانه خودتان Merge کنید. اگر Workflow به دلیل تنظیمات دسترسی GitHub نتوانست PR یا CI را ایجاد کند، عملیات متوقف است و باید قابلیت مجاز ساخت PR/اجرای Actions توسط GitHub Actions در تنظیمات مخزن بازبینی شود. برای دورزدن کنترل‌ها توکن دائمی با دسترسی گسترده تعریف نکنید.

## ۳. انتشار واقعی — فقط با اجازه جداگانه
**تصمیم مالک برای پروژه شخصی:** فعال‌سازی **Immutable Releases** و ساخت Secret اضافی انتشار لازم نیست. همین Workflow با `GITHUB_TOKEN` و مجوزهای محدود خود اجرا می‌شود. کنترل‌های اصلی شامل تأیید صریح `PUBLISH`، برابری Candidate با سورس بازبینی‌شده، موفقیت آزمون‌ها، نبود نسخه تکراری، و بررسی ZIP پس از دانلود همچنان الزامی‌اند.

پس از Merge شدن **همان PR که CI موفق و تأییدشده دارد**، در **Actions → Owner-authorized production publication → Run workflow** روی `main` مقدار `PUBLISH` را وارد کنید. نسخه را دستی وارد نمی‌کنید. سیستم نسخه، مبنای ثبت‌شده، PR یکتای مرتبط، هویت یکسان درخت فایل‌های Candidate و `main`، **هر دو CI موفقِ اجراشده با `workflow_dispatch` روی Head همان PR**، تعارض Tag/Release، ZIP و SHA-256 را دوباره بررسی می‌کند، سپس در GitHub Release نسخه را با ZIP و Checksum منتشر می‌کند. ZIP را دوباره از GitHub دانلود، بررسی و در WordPress آزمایشی با وابستگی‌های واقعی نصب می‌کند. در انتها Candidate Marker را از `main` حذف می‌کند. طبق رویهٔ این پروژه Tag و فایل نسخه قبلی جایگزین نمی‌شوند؛ بااین‌حال چون Immutable Releases الزامی نیست، GitHub خودِ این ممنوعیت را به‌صورت فنی تضمین نمی‌کند. برای اصلاح، نسخهٔ جدید منتشر کنید.

## ۴. خطا و بازیابی
تا وقتی **نتیجه مثبت خود Workflow انتشار** ثبت نشده، وضعیت `PUBLISHED_AND_CONSUMER_VERIFIED` را ادعا نکنید. اگر خطا قبل از ساخت Tag رخ داده، علت را رفع و فقط پس از بررسی وضعیت دوباره آماده‌سازی/اجرا کنید. اگر Tag، Draft Release یا Release منتشرشده ایجاد شده است، **همان عملیات را کورکورانه تکرار نکنید**. Tag را جابه‌جا نکنید؛ ZIP یا Checksum منتشرشده را جایگزین نکنید و History را Force Push نکنید. وضعیت ناقص را بررسی کنید و درباره Release اصلاحی با نسخه جدید تصمیم بگیرید.

**سوابق تاریخی Candidate:** PR #14 یک Candidate قدیمیِ منتشرنشده بود. PR #15 چرخه را اصلاح کرد و PR #16 Candidate نهایی را با CI موفق به `main` ادغام کرد. انتشار `v2.1.0` در اجرای `39419857317` موفق بود و نشانگر Candidate مصرف‌شده بعد از راستی‌آزمایی مصرف‌کننده از `main` حذف شد. این رویدادها پایان یافته‌اند و دستور اقدام بعدی نیستند. هر Candidate جدید باید با نسخه و Commit مبنای جدید، طبق همین کنترل‌ها ساخته شود.

**محدودیت:** Dry-run و تست مصنوعی وردپرس معادل صحت روی سایت واقعی، محیط واقعی کاربران یا انتشار واقعی نیستند.
**یادآوری ۲۴ اکتبر ۲۰۲۶:** موفقیت آزمایش ZIP ساخته‌شده از main حاوی NEW به معنی انتشار همان کد نیست. در انتشار بعدی علاوه بر رفع مشکل عمومی پس از Tag، exact-head مرورگر/NEW/ACK باید در ZIP کاندیدای واقعی دوباره تأیید شود. اجرای PUBLISH برای v2.1.1 مجاز نیست؛ گذشته باید دست‌نخورده بماند.


## اصلاح کنترل پس از انتشار برای نسخه‌های آینده (پیشنهاد بازبینی)

در Workflow عمومی، بررسی کوتاه `git ls-remote ... ^{}` با کنترل خواندنی API گیت‌هاب جایگزین شده است. کنترل جدید شیء دقیق تگ علامت‌دار را با SHA ساخته‌شده در همان اجرا و Commit بازبینی‌شده مقایسه می‌کند. شناسه Release و هر سه Asset فقط پس از تطبیق نام، اندازه و SHA-256 آنها با فایل‌های همان اجرا ثبت می‌شود و قبل از حذف Candidate Marker دوباره کنترل می‌شود. خطای موقت 404/429/5xx تعداد محدودی تلاش مجدد دارد؛ نوع شیء اشتباه، Commit متفاوت، Asset متفاوت و خطای حل‌نشده فوراً مانع ادامه‌اند.

این تغییر تا زمان بازبینی و Merge PR، بخشی از Workflow اصلی روی `main` نیست؛ حتی پس از Merge نیز Dry-run و CI جای اجرای واقعی Publication را نمی‌گیرند. انتشار بعدی همچنان فقط با Candidate مستقل، دو CI دقیق، تصمیم و ورودی صریح `PUBLISH` مجاز است. در صورت شکست پس از شروع Push تگ، وضعیت می‌تواند «انتشار نیمه‌تمام یا نامعلوم» باشد: پیش از هر اقدام، GitHub Tag/Release/Assets و Candidate Marker را بررسی کنید؛ تگ یا Asset موجود را بازنویسی یا تکرار کورکورانه نکنید. بازیابی تاریخی v2.1.1 و فایل‌های عمومی آن بدون تغییر باقی می‌مانند.
