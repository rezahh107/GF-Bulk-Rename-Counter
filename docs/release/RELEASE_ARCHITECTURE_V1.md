## Boundaries and invariants
- `scripts/release/release.py` is the only packaging/validation implementation. Version, strict allowlist, source dirty check, Git HEAD/tree identity, per-file hashes, manifest and ZIP SHA-256 sidecar are verified. ZIP ordering/timestamps are stable; deterministic bytes are regression tested.
- `release-prepare.yml` on explicit Owner input creates a candidate branch named `release-candidate/v<version>-from-<complete-base-commit-SHA>`, plus a review PR, and dispatches CI at that exact Head (GitHub-generated PRs may require approval). This source-bound name is unique across different main/source bases even when an earlier merged PR or remote branch already used the same version. An existing branch of the *same base* still stops creation; never overwrite/reuse it. The Owner reviews CI and merges separately.
- `release/candidate.json` keeps its existing schema 1 fields: source base Commit+Git Tree, intent, version and unique branch. It is **not** included in the ZIP. Publication validates the branch against the full source SHA and resolves **exactly one** merged PR matching that branch, target `main`, and the recorded original PR base SHA; historical same-version PRs are ignored, duplicate branch claims fail closed. Then it verifies the exact PR Head SHA and reviewed Git Tree against current integrated `main`. This works with merge, squash and rebase **only when the final tree is identical**. Subsequent unrelated modifications fail closed.
- `release-dry-run.yml` is read-only and uses the canonical builder and mutation tests. It may upload a non-production Actions artifact but cannot tag or publish.
- `release-publish.yml` requires explicit `PUBLISH`, exactly one source-bound merged candidate PR, successful workflow-dispatched dry-run **and** native integration CI for its exact reviewed SHA and branch, version/history/conflict checks, and clean unchanged `main` before mutating. The Owner's personal-project decision removes any requirement to enable Immutable Releases or configure `BRC_RELEASE_ADMIN_READ_TOKEN`. The workflow uses the scoped built-in `GITHUB_TOKEN`, a non-canceling concurrency group, and job-specific `contents:write`/`actions:read` permissions.
- Distribution: GitHub Release, with draft + ZIP/checksum/manifest before publication. No WordPress.org auto-publishing. Consumer ZIP is re-downloaded; release tag/status, exact bytes, checksum, source identity, and activation in fresh pinned WordPress with authentic dependencies are checked. Cryptographic immutable-release attestations are not required; the selected repository setting may allow future asset/tag edits, so the workflow never overwrites an existing version.
- Post-publication maintenance removes only the consumed candidate marker in a normal fast-forward commit. If `main` changed meanwhile, the workflow stops, leaving the published artifact alone. An unsuccessful last-mile or cleanup step is **partial publication**, never a silent rollback.
- Release conflict: any existing version Tag or Release, inconsistent existing history, uncertain candidate identity or missing CI blocks publication. A replacement tag/upload/release and force-push are not recovery actions.

## Evidence and limits
- PHP canonical checks exercise source PHP only.
- Release unit/mutation tests exercise parser, version, content, archive, source and review binding failures in isolated temporary repositories.
- Native integration workflow tests actual GF/Bulk Download hook, downloads, and source preservation using the installable ZIP in synthetic WordPress.
- A successful dry-run alone does **not** prove publication or consumer download. For `v2.1.0` those separate outcomes were tested in publication run `39419857317`, including downloaded-byte comparison and fresh WordPress activation; that still does **not** prove production-site equivalence, Windows extraction, or future releases. Immutable Releases are not an Owner requirement.
- The Owner controls subsequent publication and any recovery. No tagging/merging/publication is authorized by an infrastructure or documentation PR alone.
