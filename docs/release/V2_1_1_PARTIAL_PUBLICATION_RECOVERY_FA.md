# بازیابی کنترل‌شدهٔ انتشار نیمه‌تمام v2.1.1

## واقعیت تأییدشده — ۲۳ اکتبر ۲۰۲۶

- GitHub Release عمومی [v2.1.1](https://github.com/rezahh107/GF-Bulk-Rename-Counter/releases/tag/v2.1.1) وجود دارد و سه فایل ZIP، SHA-256 و Manifest آن منتشر شده‌اند.
- اجرای اصلی [40017310504](https://github.com/rezahh107/GF-Bulk-Rename-Counter/actions/runs/40017310504) با FAILURE خاتمه یافته است.
- ساخت و انتشار فایل‌ها، دانلود مجدد و مقایسهٔ بایت‌ها، و `release.py validate` برای همان ZIP موفق بوده‌اند؛ SHA-256 بستهٔ عمومی `a57b5bf3c9be6bbe6bd13af7dc415f98dba62c14e57bc0349cdf48820ff7ab39` است.
- لاگ پس از بررسی فایل‌ها و قبل از `consumer-smoke.sh` متوقف شده است. عبارت `git ls-remote --tags ... refs/tags/v2.1.1^{}` محل شکست محتمل و تقریباً قطعی در ترتیب لاگ است؛ **علت زیرساختیِ اینکه در آن لحظه جواب نداد ثابت نیست**. API کنونی GitHub تأیید می‌کند تگ علامت‌دار به Commit منتشرشده `b9e86d15f04a030f1a4c75abc2491461e75022dd` اشاره می‌کند.
- یک مانع بالقوهٔ بعدی نیز دیده شد: `consumer-smoke.sh` نسخهٔ دقیق PHP 8.2.34 را می‌خواست، اما runner نسخهٔ 8.2.35 را نصب کرده بود. این ادعای «شکست بعدی قطعی» نیست، چون اجرای اسکریپت به آنجا نرسید.
- `release/candidate.json` هنوز روی main است؛ نه پاک‌سازی نهایی انجام شد و نه موفقیت نصب ZIP عمومی اثبات شد.

## مسیر بازیابی بدون تغییر انتشار

PR اختصاصی بازیابی، Workflow جدید `Recover v2.1.1 published consumer verification (no republish)` را به مخزن اضافه می‌کند. این Workflow تنها با درخواست آگاهانهٔ مالک، ورودی دقیق `RECOVER-v2.1.1` و روی `main` اجرا می‌شود.

۱. همان Release/Tag عمومی را با شناسه‌های ثابت، نوع تگ و SHA دقیق بررسی می‌کند و از نبودن تغییرات ناخواسته مطمئن می‌شود.

۲. همان سه فایل منتشرشده را دوباره دریافت می‌کند؛ بدون آپلود، تعویض فایل یا ساخت تگ. فایل را با نسخهٔ دقیق سورسی که تگ به آن اشاره می‌کند مقایسه و مجدداً اعتبارسنجی می‌کند.

۳. روی WordPress و وابستگی‌های واقعیِ آزمایشی، **همان ZIP دانلودشده از GitHub** را نصب و فعال می‌کند. اسکریپت آزمون همچنان PHP 8.2 را الزام می‌کند، اما شمارهٔ Patch ثابت و قدیمی را الزام نمی‌کند. فقط همین خط از اسکریپت smoke تغییر کرده است.

۴. فقط پس از موفقیت تمامی مراحل، با بررسی عدم تغییر main، نشانگر `release/candidate.json` را با یک Commit معمولی حذف می‌کند. اگر هر مرحله شکست بخورد، حذف نشانگر نباید انجام شود.

**ممنوع:** اجرای دوبارهٔ Workflow `PUBLISH`، جابه‌جایی/حذف/جایگزینی Tag و Release و ZIP، Force Push یا اعلام `PUBLISHED_AND_CONSUMER_VERIFIED` قبل از نتیجهٔ مثبت Recovery.

این روش Release جدیدی نمی‌سازد و سایت شخصی Owner را تغییر نمی‌دهد. موفقیت WordPress آزمایشی، رفتار همان سناریوهای آزموده‌شده را تأیید می‌کند، نه نصب یا صحت در سایت اصلی.

## پس از Merge PR بازیابی

Branch برابر `main` باشد و در کادر تأیید **`RECOVER-v2.1.1`** وارد شود. اجرای موفق باید عبارت `RECOVERED_EXISTING_PUBLIC_V2_1_1_CONSUMER_VERIFIED_AND_MARKER_RETIRED` را گزارش دهد؛ سپس تگ/Release و حذف دقیق نشانگر روی main دوباره بررسی شوند.

برای نسخه‌های بعدی، مشکل احتمالی دیده‌شدن تگ باید جداگانه و محدود در کنترل‌های عمومی Workflow انتشار اصلاح و آزموده شود. این بازیابی اضطراری را به مجوز تغییر گذشتهٔ Release تبدیل نکن.
